## Fondo: qué necesita este sitio

Es un sitio editorial en español con guías sobre perros mayores, fuentes, autoría organizativa, publicidad, un asistente generativo y herramientas locales. El recorrido prioritario es descubrir → encontrar → leer íntegramente → conservar advertencias y fuentes → citar la URL canónica. El beneficio adicional comprobable es ejecutar cálculos existentes con la misma metodología que la interfaz. No hay evidencia de una necesidad actual de cuentas de agentes, delegación de tareas, identidad saliente firmada ni checkout.

La mejor arquitectura para ese recorrido no exige todos los protocolos. Una proyección estática completa y citable, acompañada de un índice y una skill de uso real, puede aportar gran parte del valor con pocos puntos de operación. La API determinista tiene sentido si mejora búsqueda o cálculo; el servidor MCP y WebMCP son vías de acceso opcionales a esas capacidades. OAuth y A2A no deben convertir un blog en un producto distinto para aprobar un control.

F0 acierta al investigar el límite entre assets y Worker y la paridad editorial antes de entregar Markdown. Pero agrupa un producto de auditoría permanente bastante amplio, dos mediciones externas, inventario completo, fixtures y cuatro spikes con cierre obligatorio. Esa inversión debe evaluarse frente a 28 documentos previstos y el mantenimiento del blog. Es razonable conservar medición e inventario; no está demostrado que todas las puertas de F0 deban impedir publicar una política y enlaces estáticos de F1.

### Score, nivel y utilidad son resultados distintos

- Score: proporción de pass entre controles puntuables de un perfil. El replay de los bytes guardados permite 43 Content, 20 All UI y 19 API histórica. No identifica por sí mismo calidad editorial ni capacidad real.
- Nivel: clasificación devuelta por el evaluador. No se deduce del score; un 100 Content no prueba nivel 5.
- Control estructural: presencia y forma de un descriptor, cabecera o registro. Puede aprobar sin que el servicio anunciado sea útil o funcione.
- Utilidad: un agente encuentra la guía correcta, lee texto completo con límites y fuentes, cita y, si aplica, obtiene un cálculo correcto. Requiere pruebas de recorrido y paridad adicionales al scan.

La guía primaria guardada, evidencia/referencias/scan-site.md:63–68, describe nivel 3 mediante Markdown, nivel 4 con **una** de MCP, A2A, skills o API Catalog, y nivel 5 con dos condiciones adicionales entre Web Bot Auth, todas las integraciones y auth metadata. No define completamente «todas las integraciones». El único nextLevel real guardado apunta a nivel 2 y Content Signals. No hay demostración de los requisitos efectivos para 5 en este sitio.

Recomiendo nivel 3 como primer hito y explorar nivel 4 mediante una integración mínima que funcione. Bajo los estados congelados, F1+F2 proyectan 86/100 Content y 40/100 All UI; una skill adicional proyectaría 47/100 All UI. Son cálculos condicionales, no resultados del servicio. DNS-AID real llevaría ese recorrido a 100 Content y, con la skill, aproximadamente 53 All UI si no cambian neutrales ni denominador. El 80 All UI previsto exige las ocho mejoras públicas del plan; no es el «mínimo bueno» del blog. El 100 general y nivel 5 son máximo teórico por investigar, sin compromiso de producto ni garantía técnica.

Mantener los dos perfiles congelados al informar resultados. Cuando una capacidad no aplique, explicar la brecha en All UI; no quitar controles para presentar una subida ni denominar al techo editorial «máximo posible» absoluto.

## Hallazgos ordenados por severidad

Los hallazgos marcados «fallo cierto» son contradicciones o ausencias verificables. «Decisión discutible» indica un juicio de proporcionalidad que requiere decisión del propietario/coordinador.

### A01 — Bloqueante — H1 obligatorio que no existe en un documento requerido

**Tipo: fallo cierto.** Referencias: fases/f0-contratos.md:111,125,127; fases/f0-medicion-y-contratos.md:59,81–83,146. Código: src/pages/herramientas/selector-movilidad-perros-mayores.astro:6,96,143; src/layouts/BaseLayout.astro:48,458.

Evidencia: el selector de movilidad está incluido obligatoriamente como document. Inventory exige title procedente de h1 editorial, string, y reserva null para excluded. La página no contiene ningún h1; su primer título editorial es h2 en la línea 143. BaseLayout pone el título en head, pero no añade h1. F0 prohíbe modificar las páginas.

Impacto: el inventario exhaustivo de C06 no puede ser válido sin violar al menos una obligación: inventar el h1, cambiar producto fuera del alcance o excluir una herramienta requerida. La carencia tampoco aparece en los seis fixtures, que solo incluyen la calculadora.

Corrección recomendada: el coordinador debe fijar un fallback de metadata existente con procedencia explícita, separando title de h1 observado, o resolver el H1 en una tarea de producto independiente y actualizar deliberadamente la base. Conservar la herramienta en el inventario. Añadir un caso que cubra documento sin H1; no permitir que el implementador improvise.

### A02 — Bloqueante de preparación — La base publicada que exige el prompt aún no contiene la SDD

**Tipo: fallo cierto sobre el estado de entrega, no contradicción permanente del diseño.** Referencias: fases/f0-medicion-y-contratos.md:20–28; fases/f0-prompts.md:15–18; README.md:4,39.

Evidencia: el prompt manda traer origin/docs/agent-readiness-plan y verificar los documentos F0; la entrada auditada declara que estos bytes todavía no están publicados. HEAD contiene el plan previo; los documentos F0 se ven como añadidos/modificados locales.

Impacto: un implementador nuevo no obtiene esta spec ejecutando el prompt. C01 no está preparado; el estado «lista» omite una dependencia real. Resolver un SHA una vez congela la base durante la ejecución, pero no fija previamente cuál contiene la versión auditada.

Corrección recomendada: después de corregir y verificar la SDD, publicarla como documentación, fijar su SHA completo en el lanzamiento y referenciar la versión auditada. Hasta entonces mantener el estado preparado documentalmente/con bloqueo de publicación, sin lanzar implementación.

### A03 — Alto — Compare exige fórmula/version que el summary no puede almacenar

**Tipo: fallo cierto de contrato.** Referencias: fases/f0-contratos.md:42–68,74,95–99; fases/f0-medicion-y-contratos.md:69,143.

Evidencia: summary tiene una lista cerrada «sin extras», sin campo de fórmula ni versión de reglas de scoring. Compare exige coincidencia de fórmula/version y contempla SCORING_CHANGED.

Impacto: el ejecutor debe inventar un campo prohibido, tratar schemaVersion como versión implícita sin que esté especificado o producir una comprobación que no pueda detectar el cambio esperado. Afecta directamente C03 y la reproducibilidad de comparaciones.

Corrección recomendada: fijar un identificador de reglas de scoring serializado o declarar normativamente que la versión del envelope determina esas reglas y cómo se valida una versión incompatible. Añadir fixture de scoring incompatible. Mantener aparte la versión/origen del evaluador: el hash del universo detecta IDs/categorías, pero no cambios internos de criterios.

### A04 — Alto — Metadata HTTP obligatoria sin ubicación normativa de almacenamiento

**Tipo: fallo cierto de contrato incompleto.** Referencias: fases/f0-contratos.md:36,40–78; fases/f0-medicion-y-contratos.md:73,145.

Evidencia: se exige conservar status/Content-Type de la respuesta live y distinguir la ausencia en replay. request.json es el body exacto enviado, response.raw.json es solo el body, summary prohíbe extras y no tiene campos HTTP; manifest enumera esquema, sourceCommit, recordedAt y archivos, sin definir esta metadata.

Impacto: dos implementadores pueden guardar evidencias incompatibles o perder la diferencia entre un HTTP 500 y un body de error con 200. El verificador no tiene un archivo/campo contractual que comprobar.

Corrección recomendada: definir un response-metadata.json o un objeto HTTP permitido, con status, MIME y lista acotada de headers seguros; null explícito en replay histórico. Definir quién lo incluye en manifest y los límites de truncado/fallo de body. Conservar los bytes originales y no añadir headers sensibles.

### A05 — Alto — La secuencia convierte integraciones opcionales en obligación para un blog

**Tipo: decisión discutible de producto y arquitectura.** Referencias: plan.md:9–28,62–111; README.md:25–27; evidencia/referencias/scan-site.md:67–68.

Evidencia: el cierre de F5 depende de F4B y obliga API+skills+ARD+WebMCP+MCP antes del hito público, aunque nivel 4 solo exige una integración según la guía guardada. DNS se pospone detrás de varias capas que no son requisito general de lectura.

Aumenta la superficie de versiones, errores y abuso sin demanda demostrada. El plan reconoce autenticación condicionada, pero no ofrece el mismo punto de decisión a MCP/WebMCP.

Corrección recomendada: separar itinerario editorial obligatorio de ampliaciones opcionales. Terminar lectura/citación y evaluar uso. Probar una skill útil o un catálogo de API si la API ya es necesaria. Autorizar API de cálculo, WebMCP y MCP de manera independiente a partir de clientes/recorridos concretos. DNS puede estudiarse contra destinos ya reales sin requerir siempre MCP.

### A06 — Medio — Evidencia replay reconstruida se presenta como solicitud histórica exacta

**Tipo: fallo de precisión de evidencia.** Referencias: evidencia/README.md:8,16; fases/f0-contratos.md:11,36,40,65. Evidencia: evidencia/scan-requests.json.

Evidencia: el baseline guarda el body de cada request como objeto JSON, y hashes de las respuestas. No guarda los bytes del request HTTP histórico ni su hash independiente. Espacios, orden original de serialización y newline no pueden recuperarse desde ese objeto.

Impacto: puede verificarse el body semántico y el hash de los bytes reconstruidos, pero no afirmar integridad de los bytes históricamente enviados. La solicitud live futura sí puede preservarse exactamente.

Corrección recomendada: distinguir request reconstruido en replay de request capturado live; etiquetar procedencia y mantener la representación semántica original. No inventar una prueba retroactiva de byte exacto. La ausencia no invalida el score de las respuestas originales.

### A09 — Medio — Matriz Accept no cierra todos los errores ni los headers de variante

**Tipo: contrato incompleto acotado al spike.** Referencias: fases/f0-contratos.md:142,150–170; fases/f0-medicion-y-contratos.md:117,150.

Corrección recomendada: añadir pocos casos frontera representativos y fijar alcance HTTP de errores. Mantener separado un header inválido de una ruta inexistente. **Tipo: brecha de cobertura, no fallo de filtración demostrado.** Referencias: arquitectura.md:58; fases/f0-medicion-y-contratos.md:115–119; fases/f0-contratos.md:168. Código: src/middleware.ts:39–44,76–85.

## Matriz de aplicabilidad actual

«Esencial» significa necesario para el recorrido o una decisión explícita del propietario, no necesariamente exigido por todos los agentes. «Útil opcional» puede justificar adopción con poco coste o clientes concretos. «Condicionado» requiere una nueva necesidad o interfaz de producto. «No aplicable hoy» describe el producto observado, no una prohibición perpetua.

| Capacidad | Clasificación | Justificación y evidencia funcional necesaria |
|---|---|---|
| robots.txt y acceso a bots de lectura/búsqueda | Esencial | Lectura pública deliberada; no bloquear por nombre a clientes autorizados. Probar HTTP y revisar reglas reales de zona cuando sea posible. |
| Sitemap canónico | Esencial | Descubrimiento del corpus y coherencia de publicación; destinos válidos y exclusiones justificadas. |
| Link HTTP de descubrimiento | Útil opcional, prioritario | Bajo coste; anuncia recursos existentes. Un header presente no prueba destinos ni recorrido. |
| Markdown íntegro y negociación | Útil opcional, prioritario para el objetivo | HTML ya legible, pero MD facilita extracción y citas y es requisito de nivel 3 en la guía. Paridad editorial y URLs son más importantes que MIME aislado. |
| llms.txt | Útil opcional, prioritario | Índice breve y rutas reales; sin aceptación universal demostrada ni control propio entre los siete del perfil Content. Evitar corpus monolítico duplicado. |
| Content Signals | Esencial por decisión del propietario | Expresa search=yes, ai-input=yes, ai-train=no; no es control técnico de cumplimiento por terceros. |

| API de las calculadoras | Útil opcional | Beneficio concreto: mismo cálculo sin manejar sliders. Preservar metodología y limitaciones; no necesita auth por defecto. |

## Política de contenido: coherencia sin impedir lectura autorizada

La decisión search=yes, ai-input=yes, ai-train=no es compatible con un blog abierto que desea ser encontrado y usado como contexto por agentes. Debe expresarse con los tres valores bajo el grupo relevante de robots, conservando Allow y sitemap. Search y ai-input son usos diferentes: permitir indexación no sustituye permitir lectura como contexto; prohibir entrenamiento no implica prohibir inferencia/recuperación autorizada.

El código actual de public/robots.txt solo contiene User-agent: *, Allow: / y Sitemap. No tiene Content Signals ni grupos específicos que los contradigan. Añadir la preferencia allí es un cambio pequeño. El ejemplo de la guía guardada usa ai-input=no; **no debe copiarse literalmente**, porque contradice la autorización del propietario.

Auditar el resultado final servido, incluyendo posibles inserciones de AI Crawl Control, robots gestionado, WAF y grupos específicos. No bloquear indiscriminadamente familias completas de bots que realizan búsqueda o recuperación además de entrenamiento; separar usos cuando el proveedor ofrezca agentes distintos. No usar variaciones por User-Agent para degradar o esconder contenido autorizado. Una prueba con User-Agent ficticio no establece identidad ni acceso desde las redes de proveedores.

La preferencia no acredita enforcement ni impide técnicamente que terceros ignoren la señal. No prometer «entrenamiento bloqueado» solo por publicar el directive. Cloudflare de zona debe verificarse antes de afirmar una aplicación técnica adicional.
