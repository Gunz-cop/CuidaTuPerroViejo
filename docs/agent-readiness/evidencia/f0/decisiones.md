# Propuestas de decisión F0

Estas cinco recomendaciones las presenta el implementador para ratificación del coordinador. Son opciones de diseño para F1/F2; F0 no las convierte en arquitectura aprobada ni en implementación de producción.

| Decisión | Recomendación | Alternativa descartada | Evidencia reproducible | Límite y criterio para F2 |
|---|---|---|---|---|
| Entrada y delegación | Conservar el adapter Astro y usar su `@astrojs/cloudflare/handler` como fallback; reservar Worker-first para las rutas de negociación y las exclusiones API/admin ya fijadas. | Sustituir el entrypoint del adapter o enviar todas las rutas al Worker de negociación. | Spike `4d0863c…`; build explícito, configuración compilada, preview local; 40 checks. Comprueba home/Cushing en ambos formatos y delegación del catálogo Assistant. | El preview fue local y el CDN no se probó. F2 debe validar routing en preview aprobada, preservando seguridad, APIs, admin, redirects y rutas no negociables. |
| Hook de build | Generar las proyecciones después de tener HTML renderizado y antes de empaquetar assets; hacer fallar el build ante error del generador. | `postbuild` separado o escribir artefactos después del build, que no demostraría empaquetado. | Build explícito positivo y negativo, `build-proof.json`, dry-run de la configuración compilada con assets empaquetados. | El smoke de Workers Builds de la cuenta no se ejecutó. F2 debe verificar su pipeline exacto y que el fallo impide promover/avisar indexación. |
| Selección editorial | Usar reglas DOM por tipo de página, basadas en HTML renderizado; retener avisos, FAQ y fuentes, y excluir solo chrome/UI/ads/TOC identificados. | Selector compartido de `main.textContent`, conversión regex de MDX o eliminar todos los `aside`. | Siete fixtures permanentes y siete del spike con manifests; casos de home, dos layouts de pilar, Cushing, incontinencia y herramientas. | La conversión del spike es un experimento y solo genera home/Cushing. F2 requiere revisar toda la selección de las 28 rutas, fuentes completas, controles de omisión y revisión editorial. |
| Caché y validators | Mantener Markdown en rutas estáticas por ID y distinguir representación en ruta/validator; mantener `Vary: Accept` en URLs negociadas y nunca persistir Authorization. | Reutilizar una URL/validator/cache key de HTML para Markdown o depender de una HIT aparente. | Preview local: alternancias HTML↔MD estables, ETags separados, 304 solo en mismo formato, validators cruzados 200; `edgeCache=null`. Las rutas HTML estáticas retornan desde ASSETS antes del middleware, así que no se observó una HIT/MISS de la Cache API en esta prueba. | CDN no verificado. F2 debe probar claves, TTL/purga, headers y variantes en preview pública aprobada; no usar query visitante como dimensión de contenido. |
| IDs y rutas | Usar IDs semánticos versionados y allowlist explícita (`home`, `article--<slug>`), con índice JSON que apunta a la ruta Markdown; canonical y ruta pública son datos distintos. | Derivar rutas de entrada arbitraria, ordinales o slug de categoría para identidad persistente. | Contrato `f0-contratos.md`; inventario limpio 28 documentos; prototipo indexa dos documentos con canonical URL y markdownPath explícitos. | No se aprobó el schema final, el tamaño ni la migración de IDs del corpus. F2 debe congelar todos los IDs/collisiones/legacy y validar el schema con el inventario completo. |

El coordinador debe ratificar, cambiar o diferir cada recomendación. Las limitaciones anteriores permanecen incluso si se acepta la dirección propuesta.
